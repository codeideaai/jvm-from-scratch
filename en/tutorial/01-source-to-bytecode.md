# 01 From Source Code to Bytecode

[English](01-source-to-bytecode.md) · [中文](../../tutorial/01-从源码追到字节码.md)

When you run `java OrderTotal`, the processor ultimately executes machine instructions. Two transformations are easy to confuse: javac compiles Java source into bytecode; the runtime can then interpret that bytecode or compile it into native code. Establishing this distinction gives the later performance experiments a common frame of reference.

We will start with an order-total function. Running it answers “Is the calculation correct?” Inspecting the class file answers “What did the compiler give the JVM?”

## Build the mechanism model

A class file is not compressed source code. It contains a version, a constant pool, fields, methods, and attributes. A method's Code attribute can include bytecode, an exception table, and debugging information. Abstract methods do not have a Code attribute like ordinary concrete methods.

The JVM frame model includes local variables and an operand stack. Local variables hold parameters and intermediate values; instructions push operands onto the stack and consume them to perform operations. This is the logical bytecode execution model. It does not require every instruction generated by a JIT compiler to manipulate a physical operand stack.

For integer multiplication, the operands are loaded before `imul` consumes them and produces a result. Follow the movement of values instead of trying to map each source line to exactly one instruction.

## Complete code

Save this as `Demo01.java`. It uses only the JDK 17 standard library and compiles independently.

```java
public class Demo01 {
    static int total(int price, int count, int discount) {
        return price * count - discount;
    }
    public static void main(String[] args) {
        int value = total(12, 3, 5);
        if (value != 31) throw new AssertionError(value);
        System.out.println("total=" + value);
    }
}
```

## Compile and run

```bash
javac --release 17 -encoding UTF-8 Demo01.java
java Demo01
```

Expected output (default verification mode):

```text
total=31
```

## Interpreting the evidence

Run `javap -c -p Demo01` and find total. Its three int parameters occupy local-variable slots 0, 1, and 2. This is a static method, so there is no implicit this parameter. After `iload_0` and `iload_1`, the operand stack holds price and count. `imul` replaces them with their product. Loading the discount followed by `isub` produces the final value, and `ireturn` returns it.

`javap -v Demo01` also shows the major version. With `--release 17`, it should be 61. The release option constrains the source language, target bytecode, and available platform APIs. Setting only a target class-file version does not prevent calls to newer APIs.

This file does not reveal the final JIT-generated machine code. A call in the bytecode need not remain a call in optimized execution. The inlining chapter continues this chain of evidence.

Additional observation commands, run in the directory containing this chapter's class files:

```bash
javap -c -p Demo01
javap -v Demo01
```

## A slower reading: three different tables

Start with [F03's instruction trace](../foundations/F03-read-bytecode.md). A local-variable table belongs to an invocation, a class-file constant pool belongs to the binary structure, and a runtime constant pool is associated with a runtime class. Similar terminology does not make them one memory area.

| Item in this chapter | Evidence | Meaning |
| --- | --- | --- |
| `total(12, 3, 5)` | main's source and call instruction | Three arguments supplied to total |
| `(III)I` | javap method descriptor | Three int arguments and an int result |
| `iload_0` | total's Code | Load slot 0 of this invocation, not heap object zero |
| `#number` | Constant-pool references | An indexed class-file relationship, not an address |

Trace the arithmetic: 12×3=36, then 36−5=31. The operand stack holds inputs and intermediate results. ireturn sends the value to main's call site, where main assigns it to value. Calling total does not erase main's own invocation state.

**Check your understanding:** renaming a source parameter generally preserves behavior; changing its value may not. Names assist people and debugging tools, while execution follows compiled structures and instructions. You do not need to memorize every mnemonic before tracing this calculation.

## Exercises and self-checks

Change the parameters to long and look for lload, lmul, and lreturn. A long uses two local-variable slots, so check the parameter indices. Then make total an instance method and explain why this takes slot 0.

Self-check: does javap prove that the CPU executed an imul instruction? No. Here imul is a JVM bytecode mnemonic, not a measurement of native execution.
