# F06 把线程时序画出来再谈可见性

[English](../en/foundations/F06-threads-and-order.md) · [中文](F06-把线程时序画出来再谈可见性.md)

## 一个进程可以有多条执行路线

线程可以理解为进程中的一条执行路线。两个线程各自有方法调用状态，但可以通过引用访问同一个对象。并发表示任务执行存在交错或重叠；即使只有一个 CPU 核，也能因调度交替形成并发。多核同时执行是并行，并不是产生并发错误的必要条件。

`start()` 请求启动线程执行 run；直接调用 `run()` 则是当前线程的普通方法调用。`join()` 等待目标线程结束，它不是把两个线程“合并成一个”。主线程结束前用 join 收集结果，也提供了结束后的观察顺序。

## value++ 不是一个不可拆分的动作

把它暂拆成“读 value 到临时值 → 加一 → 写回”。设共享 value 从 0 开始，可以出现下面的合法交错：

| 时刻 | 线程 A | 线程 B | 共享 value |
| --- | --- | --- | --- |
| 1 | 读取 0 | | 0 |
| 2 | | 读取 0 | 0 |
| 3 | 把 1 写回 | | 1 |
| 4 | | 把 1 写回 | 1 |

两个增量操作最终只留下 1。即使每次读取都读到了当时的最新值，结果也会如此，所以它不必依赖“某个核心缓存一直没刷新”的故事。

下面使用 CyclicBarrier 让两个线程都读完才允许写回，专门把这个时序固定下来。屏障只是实验用的集合点：两个参与者都到达后才继续，并设置超时防止实验错误时永久等待。**这是人为安排交错来解释复合操作，不是对随机线程调度概率的测量。**

## 完整代码

保存为 `Foundation06.java`.

```java
import java.util.concurrent.CyclicBarrier;
import java.util.concurrent.TimeUnit;
import java.util.concurrent.atomic.AtomicInteger;
public class Foundation06 {
    static volatile int value;
    static void await(CyclicBarrier gate) {
        try { gate.await(5, TimeUnit.SECONDS); }
        catch (Exception e) { throw new AssertionError(e); }
    }
    public static void main(String[] args) throws Exception {
        CyclicBarrier bothRead = new CyclicBarrier(2);
        Runnable splitIncrement = () -> {
            int local = value;
            await(bothRead);
            value = local + 1;
        };
        Thread a = new Thread(splitIncrement);
        Thread b = new Thread(splitIncrement);
        a.start(); b.start(); a.join(); b.join();
        if (value != 1) throw new AssertionError(value);
        System.out.println("split increment=" + value);
        AtomicInteger count = new AtomicInteger();
        Runnable atomicIncrement = () -> {
            for (int i = 0; i < 1000; i++) count.incrementAndGet();
        };
        Thread c = new Thread(atomicIncrement);
        Thread d = new Thread(atomicIncrement);
        c.start(); d.start(); c.join(); d.join();
        if (count.get() != 2000) throw new AssertionError(count.get());
        System.out.println("atomic increments=" + count.get());
    }
}
```

## 编译与运行

```bash
javac --release 17 -encoding UTF-8 Foundation06.java
java -cp . Foundation06
```

预期输出：

```text
split increment=1
atomic increments=2000
```

## 三个问题用三句话分开

**原子性：**一组读写是否必须作为不可分割的操作完成？示例的 volatile 字段不能把分开的读写自动合成一次原子加法。AtomicInteger.incrementAndGet 提供对应原子操作，所以两个线程各加 1000 次后为 2000。

**可见性：**另一个线程按什么规则能观察到写入？不能用“我等了几毫秒”代替同步协议。sleep 只是暂停执行，不自动建立你所需的跨线程发布关系。

**有序性：**哪些动作之间有规范规定的先后关系？happens-before 不是拿墙上时钟比较两行输出的时间戳，而是一套允许推导观察结果的关系。主线 10 会用一个 ready 标志串起数据发布。

## 为什么锁与 volatile 不可互换

库存“检查是否大于零，再减一”需要保护整个判定与更新过程。只把库存字段设成 volatile，不会阻止两位购买者都通过检查。用同一把锁包住整个操作，或采用适合该状态更新的原子协议，才是对这个问题的回答。

反过来，一次性发布“普通 payload 写入之后，volatile ready=true”，需要的是发布关系，不一定需要把所有读取都锁住。选择同步工具前，应先写出需要维护的不变量。

**练习与答案：**把 start 改成直接 run，本例第一个线程会在屏障等待第二个参与者，但当前线程尚未执行第二次 run，最终超时；这不是屏障失灵，而是没有真正并发启动。原子版本中把 incrementAndGet 拆成 get 加 set，也不再是一整个原子更新。此时错误结果未必每次出现，不能照抄第一部分“总为 1”的断言，因为它没有使用相同屏障安排。

能解释“最新的值也可能算出错误结果”之后，再读主线 10—11 的发布和监视器。
