# 19 扩展篇：连接编译期生成与本地执行

[English](../en/tutorial/19-extension-mechanisms.md) · [中文](19-扩展篇编译期生成与本地执行.md)

前面已经掌握 javac、class、JIT 和 agent。接下来容易把几种扩展机制混为一谈：注解处理器生成代码，JNI 调用本地代码，Graal 编译代码，Truffle 支持实现语言，Native Image 在构建时形成原生程序。它们工作的阶段和要维护的契约不同。

本篇采用一个“表达式计算服务”的设计案例：用户输入规则，服务加载规则并求值。我们分别讨论这些技术可以放在哪一层，以及哪些需求会与它们的边界发生冲突。本篇不声称运行了外部工具链。

## 注解处理器：把重复工作提前到编译期

假设每个业务模型都需要一份字段索引。运行时反射可以枚举字段，注解处理器则能在 javac 编译期间根据声明生成索引类。输入是源码层元素模型，产物可以是新的源码、资源或诊断信息。

JSR 269 的处理过程可能有多轮：生成的新源码会参与后续处理，最后一轮用于结束处理。应通过 Filer 管理产物，避免用普通文件写入绕过编译器；同一轮或跨轮反复生成同一路径会导致冲突。处理器返回的布尔值表示是否认领本轮相关注解，不是“处理成功或失败”。

注解处理器不等于任意修改现有类的受支持 API。使用非标准编译器内部接口改 AST，是另一个兼容性风险更高的方案。第 15 篇的 JMH 工程就使用处理器生成基准基础设施，只有 jmh-core 依赖而没有处理器，通常不足以得到可发现的基准列表。

对表达式服务来说，处理器适合预生成固定业务模型的访问代码；用户运行时临时输入的表达式不在当次 javac 输入中，不能指望既有处理器自动处理它。

## JNI：跨越托管代码边界

假设计算服务要调用现有 C 库。Java 用 native 方法声明入口，通过本地库加载和约定或注册方式找到实现。JNIEnv 与线程关联，不能把某个线程获得的环境指针作为跨线程通用句柄。跨边界时需要处理本地引用、全局引用以及异常状态。

JNI 局部引用有生命周期；需要长期保留 Java 对象时，应该采用相应的全局引用机制并及时释放。拥有全局引用会影响对象可达性，泄漏它可能导致 Java 堆对象长期存活。长循环里大量创建局部引用也需要管理，不应只等本地方法最终返回。

把 Java 数组交给本地代码并不意味着获得永久有效的裸指针。特定 API 可能涉及复制或固定，并要求配对释放。持有临界数组区域时，必须遵守相关阻塞和调用限制。

本地代码不受 Java 数组边界和内存安全机制的全面保护。本地库崩溃可能终止整个进程。因此如果目标只是对很短的算术操作加速，要先测量边界调用与数据转换成本，不能只比较 C 函数内部耗时。

## Graal 与 Truffle：编译器和语言框架的分工

Graal 是编译技术；“编译器用 Java 编写”并不意味着只能生成 Java 字节码。Truffle 提供实现语言解释器的框架，与优化编译协作，可以从解释器和执行信息出发专门化程序。

对表达式服务而言，可以先实现一个明确语义的表达式 AST 解释器，再考虑 Truffle 是否适合语言实现需求。这个决定与“把普通 Java 服务直接编译成本地可执行文件”不是同一个任务。

优化依赖稳定的假设。当节点见到新的类型或行为，之前的专门化可能失效。读到“自动优化解释器”时，应继续追问哪些状态作为常量、哪些输入动态变化，以及失效后如何保持语义。

## Native Image：构建时可达性与运行时动态性

Native Image 在构建时分析可达代码并生成本地程序，还需要相应运行时支持内存管理等功能。它不是把 JVM 的所有功能都原样打包，也不是生成不再需要垃圾回收的 C 程序。概念和约束见 [Native Image Basics](https://www.graalvm.org/latest/reference-manual/native-image/basics/)。

如果服务用字符串类名反射构造对象，静态分析可能无法仅从普通控制流看到目标，需要相应可达性元数据。资源文件、JNI 和代理等动态机制也需要按工具版本处理。不能以“普通 JVM 运行成功”直接推断本地镜像行为完整。

另一个边界是类初始化时间。如果把机器相关配置读取提前到构建阶段，可能把构建环境的数据固化进镜像。决策应明确哪些类在构建时初始化，哪些必须留到运行时。

HotSpot 的实验性 jaotc 路线与 Native Image 不是同一个产品路径。JDK 17 移除了当时随 JDK 提供的实验性 jaotc 工具和 Graal JIT 编译器，参见 [JEP 410](https://openjdk.org/jeps/410)。不要将历史 jaotc 命令列为本系列 JDK 17 的必做实验。

## 为计算服务做技术选择

| 需求 | 可以研究的机制 | 首先验证的边界 |
| --- | --- | --- |
| 固定模型访问代码 | 注解处理器 | 多轮生成、增量构建、诊断质量 |
| 复用已有本地库 | JNI | 数据生命周期、异常和线程契约 |
| 实现新的表达式语言 | Truffle | 解释器语义与专门化失效 |
| 改善启动与部署形态 | Native Image | 反射资源元数据、初始化时机、构建成本 |
| 研究热点编译 | Graal/JIT | 所用发行版、平台支持与测量条件 |

这些是需要验证的候选，不是固定技术推荐。先确定瓶颈来自启动、稳态吞吐、存活内存还是本地库依赖，再选择工具。若全部需求都只是普通 Java 规则计算，前面建立的字节码、JIT、GC 和 JFR 方法已经能解决许多问题。

## 自测与实践设计

为表达式服务写两份需求：一份要求任意上传 JAR 并动态加载，一份只允许发布前确定的规则。分析两者对静态可达性分析的影响。再列出三种必须在运行时读取的配置，说明提前到构建时会产生什么错误。

继续实践时，一次只接入一种外部工具链，并记录精确版本、构建命令和最小功能回归。不要同时更换编译器、GC、镜像形态和业务算法，然后把全部性能变化归给其中一个因素。
