# 09 用GC日志观察分配压力

[English](../en/tutorial/09-gc-logs.md) · [中文](09-用GC日志观察分配压力.md)

服务不断创建短命对象，吞吐量下降可能来自频繁回收，也可能来自别的瓶颈。本篇建立一个有界分配负载，用统一日志观察回收活动。程序校验与性能观测分开：校验必须稳定，回收次数和暂停时长则只能实测。

## 先建立机制模型

垃圾回收的基本工作包含找出存活对象以及回收或整理其余空间。标记、复制、整理是理解算法的组成动作；具体收集器会把它们组合到不同阶段。分代依据对象寿命的经验规律，跨代引用需要额外记录，不能简单地把年轻代当作完全独立的堆。

G1 使用 Region 组织堆空间，可按区域选择回收集合。暂停目标是调度目标而非实时上限；一次暂停还会受存活集、引用处理和系统调度影响。降低堆上限通常会增加回收压力，不是免费降低内存占用。

吞吐量、暂停分布和资源成本之间需要用负载测量做权衡。本篇显式选择 G1，避免把不同机器上的默认收集器差异带入对照。

## 完整代码

将以下内容保存为 `Demo09.java`。仅依赖 JDK 17 标准库，可独立编译。

```java
public class Demo09 {
    static volatile byte[] sink;
    public static void main(String[] args) {
        long checksum = 0;
        for (int i = 0; i < 2000; i++) {
            byte[] block = new byte[128 * 1024];
            block[0] = (byte) i;
            sink = block;
            checksum += sink[0];
        }
        if (checksum != 152) throw new AssertionError(checksum);
        System.out.println("checksum=" + checksum);
    }
}
```

## 编译与运行

```bash
javac --release 17 -encoding UTF-8 Demo09.java
java Demo09
```

预期输出（普通验证模式）：

```text
checksum=152
```

## 解释结果与证据边界

每次把新数组写入 volatile 静态字段，使分配结果向程序可观察状态发布；字段只保留最近一个数组，避免把实验变成无限增长的存活集。数组大小为 128 KiB，在本实验常见的 G1 Region 配置下不会刻意制造巨型数组路径。

额外运行下列命令，再打开 gc.log。关注使用的收集器、回收前后占用、暂停原因和时长单位。不要把日志中的总容量误读为进程的全部物理内存；线程栈、元空间、代码缓存和本地分配并不都在 Java 堆里。

把 Xmx 从 32m 改为 64m，只能形成一个容量对照。由于负载很短，不能用它挑选生产收集器；还需要长时间稳定负载、分配速率与尾延迟。统一日志参数见 [java 命令文档](https://docs.oracle.com/en/java/javase/17/docs/specs/man/java.html)。

补充观察命令，在本篇 class 文件所在目录执行：

```bash
java -Xms32m -Xmx32m -XX:+UseG1GC -Xlog:gc*:file=gc.log:time,uptime,level,tags Demo09
```

## 逐字段读一行已有实测日志

下面从本项目 validation/gc.txt 摘出一行事件主体，省略时间和级别前缀。它是一次已有实测记录，不是以后每次都应该相同的输出：

```log
GC(0) Pause Young (Normal) (G1 Evacuation Pause) 14M->1M(32M) 0.784ms
```

| 字段 | 本行中的含义 | 不该推出的结论 |
| --- | --- | --- |
| GC(0) | 关联该次事件的编号 | 0 表示没有发生 GC |
| Pause Young | 年轻代相关的暂停事件 | 整个进程终生只回收年轻代 |
| G1 Evacuation Pause | 该事件的 G1 转移暂停名称 | 已证明所有对象都移动过 |
| 14M → 1M | 回收前后的堆使用量汇总 | 进程 RSS 从 14M 变成 1M |
| (32M) | 该时刻记录的堆容量 | 进程总内存被限制为 32M |
| 0.784ms | 本次暂停耗时 | 所有请求只增加这点延迟 |

主线示例总共尝试创建 2000×128 KiB，约 250 MiB 的数组负载，但它不需要同时保留 250 MiB。**累计分配量、当前存活量、堆容量是三个数**。只保留最新数组，旧数组才有机会被回收，这就是小堆能完成较大累计分配的原因。

**两道判断题：**回收后占用低，就能证明无泄漏吗？不能，这只是短负载的一次观测。暂停更短，就能证明吞吐量更高吗？不能，更频繁的短暂停和其他 GC 工作也有成本。先保持请求模式、数据规模、时间窗口一致，再比较一组指标。

## 动手修改与自测

记录两种堆容量下的回收次数、暂停总时间和最长暂停，不预设后者一定更小。再用固定大小环形数组保留最近若干对象，比较存活集增加之后回收后占用如何变化。不要通过无限缓存触发系统内存耗尽。
