# 08 从对象引用走到垃圾回收根

[English](../en/tutorial/08-references-and-gc-roots.md) · [中文](08-从对象引用走到垃圾回收根.md)

缓存中删除一个条目，堆内存为什么没有立刻下降？这里至少有三个问题：对象是否仍被引用、是否已满足回收条件、收集器何时实际回收。把它们分开，才能避免用一次 System.gc 调用猜测内存泄漏。

## 先建立机制模型

可达性分析从 GC Roots 出发遍历对象关系。线程执行中的活跃引用、静态可达关系等可以让对象继续存活。循环引用本身不妨碍可达性分析：只要环整体不再能从根到达，它仍可以成为回收候选。

HotSpot 的对象布局通常涉及对象头、实例字段和对齐空间；引用宽度、类型指针压缩、数组长度信息都会改变尺寸。不要用“字段大小相加”作为全部堆占用，也不要把固定的对象头大小写成所有 JVM 的保证。

WeakReference 允许在弱可达时被收集器清除，但何时清除不是即时通知协议。ReferenceQueue 可以通知引用对象的入队事件；显式 clear 与 enqueue 则允许我们在不依赖 GC 时序的情况下检验处理逻辑。

## 完整代码

将以下内容保存为 `Demo08.java`。仅依赖 JDK 17 标准库，可独立编译。

```java
import java.lang.ref.ReferenceQueue;
import java.lang.ref.WeakReference;
public class Demo08 {
    public static void main(String[] args) {
        Object strong = new Object();
        ReferenceQueue<Object> queue = new ReferenceQueue<>();
        WeakReference<Object> weak = new WeakReference<>(strong, queue);
        System.out.println("same referent=" + (weak.get() == strong));
        weak.clear();
        System.out.println("cleared=" + (weak.get() == null));
        System.out.println("queue empty=" + (queue.poll() == null));
        System.out.println("enqueued=" + weak.enqueue());
        System.out.println("same reference=" + (queue.poll() == weak));
        java.lang.ref.Reference.reachabilityFence(strong);
    }
}
```

## 编译与运行

```bash
javac --release 17 -encoding UTF-8 Demo08.java
java Demo08
```

预期输出（普通验证模式）：

```text
same referent=true
cleared=true
queue empty=true
enqueued=true
same reference=true
```

## 解释结果与证据边界

strong 在实验末尾仍被 reachabilityFence 保持可达，因此输出中的清除来自我们显式调用 clear，而不是声称收集器已经回收了对象。clear 不自动入队，所以第三行为 true；enqueue 放入的是 WeakReference 本身。

生产中的弱引用缓存还需要消费队列并移除过期索引，否则即使 referent 已被回收，缓存键与引用包装对象仍可能长期累积。内存泄漏诊断应寻找“谁持有谁”，而不是只统计某个类型的数量。

变量离开源码作用域与对象失去实际活跃引用也不是一一对应关系。JIT 的活跃性分析可能提前结束引用存活时间，涉及本地资源生命周期时尤其要谨慎。

## 在弱引用前补齐“强引用还在”的判断

如果 F02 中 first 和 alias 都指向对象 A，仅将 first=null 不会让 A 消失，因为 alias 仍然是路径。若 A 还被静态缓存 entries 持有，方法返回也不能自动解除缓存这条路径。需要问的是“从哪些仍然活跃的起点能到达它”，不是统计源码中还出现几次变量名。

本篇 WeakReference 的实验只验证包装对象的 clear 与 enqueue API。它没有覆盖 GC Roots 的查找过程，也没有模拟回收器自动清除弱可达对象的时序。若初读后感觉“仍不知道为什么能回收”，先做 [F04 引用图实验](../foundations/F04-先看引用图再理解垃圾回收.md)，再回来理解弱引用是怎样改变某条边的处理规则。

**自测：**一个对象没有被业务使用，却仍在无界缓存里，JVM 应该自动猜到它没用并回收吗？不能依赖这种猜测，强可达关系仍可能保留它；应用需要实现淘汰。反过来，对象不可达就一定下一毫秒归还给操作系统吗？也不是，可回收、实际回收、进程内存归还属于不同层次。

## 动手修改与自测

增加第二个强引用 alias，删除原 strong 的赋值并不代表对象不再可达。画出 roots → 容器 → 条目 → 业务对象的引用图，指出必须断开哪条边。若另做真实 GC 实验，应允许超时且明确“未观察到回收”不等于 GC 规则错误。
