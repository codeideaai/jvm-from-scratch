# 14 理解逃逸分析循环优化与向量化

[English](../en/tutorial/14-escape-analysis-and-loops.md) · [中文](14-理解逃逸分析循环优化与向量化.md)

源码里每轮循环都 new 一个对象，为什么堆分配可能没有预想的多？原因可能是对象不必以完整对象的形式存在于最终机器码里。但“可能消除分配”与“保证在栈上分配”是两种不同结论。

## 先建立机制模型

逃逸分析研究对象能否被当前分析范围之外的代码访问。若对象的用途足够明确，编译器可以进一步做标量替换，用字段值参与计算而无需保留完整对象。分析本身与优化动作要分开：发现不逃逸，并不保证所有相关分配一定被消除。

内联扩大可见范围，有助于分析构造器、访问器和调用者之间的数据关系。反过来，把对象存入静态字段、传给无法分析的代码，都可能妨碍优化。本地 new 语句并不自动等于不逃逸。

循环优化包含不变量外提、范围检查消除、展开等；自动向量化还受数据依赖、别名、类型和目标指令集约束。intrinsic 是编译器对特定方法语义的特殊处理，不等于普通 Java 方法体被逐行翻译，也不保证所有平台走相同指令。

## 完整代码

将以下内容保存为 `Demo14.java`。仅依赖 JDK 17 标准库，可独立编译。

```java
public class Demo14 {
    record Point(int x, int y) {}
    static volatile long sink;
    static long calculate(int count) {
        long sum = 0;
        for (int i = 0; i < count; i++) {
            Point point = new Point(i, i + 1);
            sum += point.x() + point.y();
        }
        return sum;
    }
    public static void main(String[] args) {
        for (int i = 0; i < 3000; i++) sink = calculate(1000);
        if (sink != 1_000_000L) throw new AssertionError(sink);
        System.out.println("sum=" + sink);
    }
}
```

## 编译与运行

```bash
javac --release 17 -encoding UTF-8 Demo14.java
java Demo14
```

预期输出（普通验证模式）：

```text
sum=1000000
```

## 解释结果与证据边界

Point 只用于本轮求和，没有写入外部容器，是值得进一步观察的优化候选。本篇没有因为结果正确就声称标量替换发生。正确性输出只说明两条路径必须保留的语义。

用相同堆配置分别运行默认设置与 `-XX:-DoEscapeAnalysis`，观察 GC 日志或借助后文 JMH 的分配 profiler。即使观察到差异，也要考虑关闭逃逸分析可能连带改变其他优化；它不是完美隔离单个机制的实验。

若需要观察循环向量化，可另建两个数组逐元素相加，结合生成代码与硬件计数研究。这里的 Point 示例既没有证明使用 SIMD，也没有证明发生栈分配。产品版 JDK 通常不支持一些仅 debug build 提供的分析打印开关，不应把它们列成人人可用命令。

补充观察命令，在本篇 class 文件所在目录执行：

```bash
java -Xms32m -Xmx32m -Xlog:gc:file=ea-on.log Demo14
java -Xms32m -Xmx32m -XX:-DoEscapeAnalysis -Xlog:gc:file=ea-off.log Demo14
```

## 动手修改与自测

增加一个静态 volatile Point 字段并把每轮对象赋给它，重新测量分配。解释发布对象为何改变可优化范围。再把 i 扩大到接近 int 边界，检查字段相加是否先溢出，避免把整数语义变化误当优化错误。
