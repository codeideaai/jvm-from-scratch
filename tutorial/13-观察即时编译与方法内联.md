# 13 观察即时编译与方法内联

[English](../en/tutorial/13-jit-and-inlining.md) · [中文](13-观察即时编译与方法内联.md)

一个小方法被调用一百万次，是否必然产生一百万次机器层调用？JIT 的方法内联可以把被调用者逻辑纳入调用者的编译范围。它既能减少调用开销，也会给常量传播、范围分析等后续优化打开空间。

## 先建立机制模型

解释执行可以较快开始工作，同时运行时收集热点信息。HotSpot 的分层编译会在编译成本和生成代码质量之间做取舍。调用次数与循环回边都可能影响编译决策；不能把某个固定次数当成语言规则。

内联不是单纯依据源码行数。方法大小、调用点类型信息、编译预算和运行剖析都会影响判断。虚方法也可能内联：如果运行时观察到接收者类型稳定，可以基于检查和可撤销假设优化。

假设失效时，运行时可能使编译代码失效或去优化，恢复到能继续保持语义的执行状态。去优化不是把源代码“改错了”，而是投机优化机制的一部分。

## 完整代码

将以下内容保存为 `Demo13.java`。仅依赖 JDK 17 标准库，可独立编译。

```java
public class Demo13 {
    static volatile long sink;
    static int step(int value) { return value * 3 + 1; }
    static long batch(int count) {
        long sum = 0;
        for (int i = 0; i < count; i++) sum += step(i);
        return sum;
    }
    public static void main(String[] args) {
        for (int i = 0; i < 2000; i++) sink = batch(10000);
        long expected = 3L * 9999 * 10000 / 2 + 10000;
        if (sink != expected) throw new AssertionError(sink);
        System.out.println("sum=" + sink);
    }
}
```

## 编译与运行

```bash
javac --release 17 -encoding UTF-8 Demo13.java
java Demo13
```

预期输出（普通验证模式）：

```text
sum=149995000
```

## 解释结果与证据边界

普通运行仅验证结果。诊断运行开启 PrintCompilation 与 PrintInlining 后，输出会混入大量编译事件。查找 Demo13::batch 和 Demo13::step，读取它们所属的编译任务以及内联决定。某个调用点一次未内联，不代表后续更高层级编译也不会内联。

编译日志不是完整机器汇编。要判断某条本机指令是否存在，还需要合适的反汇编支持；这取决于 JDK 和平台。本系列不通过缺少汇编的情况下猜测精确 CPU 指令。

对照 `-Xint` 可以验证纯解释模式仍给出相同计算结果，但这样得到的耗时差异混合了整个运行过程。它不能隔离出“只有方法调用这一项”的成本。

补充观察命令，在本篇 class 文件所在目录执行：

```bash
java -XX:+UnlockDiagnosticVMOptions -XX:+PrintCompilation -XX:+PrintInlining Demo13 > jit.log 2>&1
```

## 先解释为什么不一启动就编译全部代码

大程序可能带着大量本次根本不会执行的方法。立即优化所有方法会消耗启动时间和编译资源，却未必换来收益。解释器先执行，运行时观察热点，再给值得优化的部分投入编译成本，是理解即时编译的一条动机线索。

在常见的 HotSpot 分层编译配置里，C1 和 C2 承担不同的编译与优化工作；0 表示解释层，1—3 与不同 C1 配置有关，4 通常对应 C2。它不是每个方法必须按 0、1、2、3、4 排队走完的升级考试。不同选项、构建与实现会改变路径。

已有日志里这两行值得连起来读：

```log
12    8 %     3       Demo13::batch @ 4 (25 bytes)
                              @ 11   Demo13::step (6 bytes)   inline
```

`%` 标识 OSR 编译，`@ 4` 是进入该已在执行的方法的字节码位置；它帮助解释“方法没有重新从头调用，也可以在热循环中切入编译代码”。缩进的第二行是在这个编译上下文中报告调用点的内联决定。数字 25 与 6 是字节码大小，不是源码行数，也不是机器码执行耗时。

**为什么预热结果会变？**首次类加载、数据访问、解释执行、编译和稳态运行可能处在不同阶段。启动速度与长期吞吐是不同目标。不要把第一轮慢直接叫作“GC 问题”，也不要因为出现 inline 一词就宣布整个程序已经最优。

## 动手修改与自测

给 step 增加少量分支，观察内联决定是否改变。随后只对比不同接收者类型分布，保持计算结果和负载规模一致。保留 JDK、CPU、参数和原始日志，再解释差异；不要只留一张耗时截图。
