# 06 沿异常表理解资源关闭

[English](../en/tutorial/06-exceptions-and-resources.md) · [中文](06-沿异常表理解资源关闭.md)

读取业务数据失败的同时，关闭资源也失败，最终应该向调用者报告哪一个异常？如果手写 finally 时直接抛出关闭异常，很可能遮住最重要的业务原因。try-with-resources 为这个问题定义了明确的处理顺序。

## 先建立机制模型

JVM 根据异常发生的位置及异常表查找匹配处理器。匹配时控制流转入处理器；找不到时当前方法异常退出，继续沿调用栈寻找。异常表描述受保护区间和处理器位置，不是每条普通指令前都写一段 catch 判断。

try-with-resources 由编译器展开资源管理流程。资源按声明的逆序关闭；当主体已经抛出异常时，关闭异常作为 suppressed exceptions 附加到主体异常。只有关闭失败而主体成功时，关闭异常才成为主要异常。

finally 一般会执行，但不能把它理解为进程被强制终止、虚拟机崩溃时仍有保证的持久化机制。尤其不要在 finally 中 return，它会覆盖原本的返回或异常结果。

## 完整代码

将以下内容保存为 `Demo06.java`。仅依赖 JDK 17 标准库，可独立编译。

```java
public class Demo06 {
    static class Resource implements AutoCloseable {
        final String name;
        Resource(String name) { this.name = name; }
        @Override public void close() {
            System.out.println("close " + name);
            throw new IllegalStateException("close-" + name);
        }
    }
    public static void main(String[] args) {
        try (Resource a = new Resource("A"); Resource b = new Resource("B")) {
            throw new IllegalArgumentException("business");
        } catch (IllegalArgumentException e) {
            System.out.println("primary=" + e.getMessage());
            for (Throwable other : e.getSuppressed()) {
                System.out.println("suppressed=" + other.getMessage());
            }
            if (e.getSuppressed().length != 2) throw new AssertionError(e);
        }
    }
}
```

## 编译与运行

```bash
javac --release 17 -encoding UTF-8 Demo06.java
java Demo06
```

预期输出（普通验证模式）：

```text
close B
close A
primary=business
suppressed=close-B
suppressed=close-A
```

## 解释结果与证据边界

两个资源都被关闭，即使 B 的 close 已经失败，编译器展开的逻辑仍会继续关闭 A。主体的 IllegalArgumentException 保留为主异常，便于定位最早的业务失败。

使用 javap 的详细输出查找 Exception table 和 addSuppressed。表中的 from 是包含的起点，to 是不包含的终点。实际偏移随编译结果变化，所以应围绕自己的 class 阅读，不要背固定偏移。

日志只打印 getMessage 会丢掉堆栈、cause 与 suppressed。应用记录异常时应交给日志框架处理完整 Throwable；这里输出消息仅为了制作稳定的教学断言。

补充观察命令，在本篇 class 文件所在目录执行：

```bash
javap -c -v Demo06
```

## 动手修改与自测

删除主体抛异常的语句，改用 catch RuntimeException，观察哪个关闭异常成为主异常。再把 A 的构造器改为抛异常，解释 B 为什么没有机会创建，以及未成功初始化的资源为什么不会进入关闭序列。
