# 18 综合实战定位无界缓存增长

[English](../en/tutorial/18-bounded-cache.md) · [中文](18-综合实战定位无界缓存增长.md)

订单服务用 Map 缓存计算结果，命中率很高并不意味着内存安全。如果键的基数持续增加且没有淘汰机制，缓存会把本应短命的对象变成长寿命对象。本篇用有限请求重现增长，并实现有容量上限的访问顺序缓存。

## 先建立机制模型

从症状到假设：请求数上升、回收后存活量也上升，可能存在长期持有对象的容器。仅看到 byte[] 很多还不足以判断原因，需要沿引用链找到容器和键。扩大 Xmx 能延后失败，但不能改变保留数量随键数增长的关系。

本例比较两个 Map：普通 HashMap 保留全部不同键，LinkedHashMap 的访问顺序模式配合 removeEldestEntry 保留最近使用的有限条目。容量以条目数计，不等于精确字节预算；真实缓存还需要考虑值大小、过期时间和并发加载。

这不是生产级并发缓存。本例单线程运行，显式限制请求数量和每个值的大小，让问题能被观察而不必先触发 OOM。

## 完整代码

将以下内容保存为 `Demo18.java`。仅依赖 JDK 17 标准库，可独立编译。

```java
import java.util.HashMap;
import java.util.LinkedHashMap;
import java.util.Map;
public class Demo18 {
    static class Bounded extends LinkedHashMap<Integer, byte[]> {
        private final int limit;
        Bounded(int limit) {
            super(16, 0.75f, true);
            if (limit <= 0) throw new IllegalArgumentException("limit");
            this.limit = limit;
        }
        @Override protected boolean removeEldestEntry(Map.Entry<Integer, byte[]> eldest) {
            return size() > limit;
        }
    }
    static void fill(Map<Integer, byte[]> cache) {
        for (int i = 0; i < 2000; i++) cache.put(i, new byte[1024]);
    }
    public static void main(String[] args) {
        Map<Integer, byte[]> unlimited = new HashMap<>();
        Bounded bounded = new Bounded(128);
        fill(unlimited); fill(bounded);
        if (unlimited.size() != 2000 || bounded.size() != 128) throw new AssertionError();
        System.out.println("unbounded=" + unlimited.size());
        System.out.println("bounded=" + bounded.size());
        Bounded order = new Bounded(2);
        order.put(1, new byte[1]); order.put(2, new byte[1]);
        order.get(1);
        order.put(3, new byte[1]);
        if (order.containsKey(2) || !order.containsKey(1)) throw new AssertionError();
        System.out.println("least recently used evicted=true");
    }
}
```

## 编译与运行

```bash
javac --release 17 -encoding UTF-8 Demo18.java
java Demo18
```

预期输出（普通验证模式）：

```text
unbounded=2000
bounded=128
least recently used evicted=true
```

## 解释结果与证据边界

前两条断言验证容量约束，最后的单独场景验证淘汰语义：访问 1 后，2 才是最久未使用的键。只检查 Map.size 而不检查访问顺序，可能掩盖实现成 FIFO 的错误。

程序输出的是条目数，不是假装测量堆的精确字节数。保留的数组、包装键、Map 节点和表数组都有各自开销。若要计算实际保留成本，可以结合上一章尺寸观察与本章引用图；复杂对象图仍需要专门的堆分析。

可进一步给程序增加观察窗口，按第 16 篇捕获线程与堆证据，然后只替换缓存策略，重复同样键分布。验收同时包含正确淘汰、结果一致、存活量有界和延迟可接受。不能以“Full GC 少了”作为唯一完成条件。

## 动手修改与自测

为负容量补一个失败用例，再让缓存值大小随键变化，分析条目上限的不足。设计一个字节预算策略，回答替换已有键时如何扣减旧权重。最后写一段故障报告：症状、假设、证据、修复、回归条件分别是什么。
